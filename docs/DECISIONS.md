# Decisions

One entry per non-obvious technical decision: context, alternatives, choice, accepted
trade-off. Newest last. A good practice deliberately skipped is worth more written down
than silently omitted.

---

## ADR-001 — An intermediate representation between capture and code generation

**Context.** The obvious build is: capture an event, append a line of Python. It is
fewer moving parts and ships faster.

**Alternatives.** (a) Generate code directly from events. (b) Store a raw event log and
generate from it. (c) Store a versioned, typed IR with a transformation pipeline
between it and the generator.

**Choice.** (c).

**Trade-off accepted.** More code and one more concept to learn before contributing.
Paid back by: passes that are pure and testable without a browser; a recording that can
be regenerated by a better generator later; a place to intervene between capture and
output, which is what makes parameterisation possible; and the ability to add the
desktop recorder without touching the web generator. The whole project's premise —
mixing capture layers of different fidelity — is impossible without it.

## ADR-002 — Secrets enforced by an invariant, not by convention

**Context.** Password values must not reach disk. The usual approach is to filter them
somewhere on the way out.

**Alternatives.** (a) Filter at write time. (b) Filter in the transformation pipeline.
(c) Make the data model unable to hold a secret and a value at the same time.

**Choice.** (c), plus (a) as a second layer. `Event.__post_init__` raises if
`is_secret=True` comes with a value, and `injected.js` never sends one.

**Trade-off accepted.** A recorder bug now crashes loudly instead of degrading quietly,
and one malformed event is skipped rather than recorded. That is the right direction to
fail in: a lost event costs a re-record, a leaked password costs trust in the tool.

## ADR-003 — Recorded timing never becomes `time.sleep()`

**Context.** The recording knows exactly how long the user waited. Emitting that as
`time.sleep(2.3)` is trivial and looks faithful.

**Alternatives.** (a) Emit the recorded pauses as sleeps. (b) Emit nothing and rely on
Playwright's auto-waiting. (c) Turn long pauses into an explicit wait for the element
the next action targets.

**Choice.** (c), with (b) as the implicit baseline.

**Trade-off accepted.** The generated code no longer reproduces the original timing,
and a pause that had nothing to do with page loading produces a harmless extra
assertion. In exchange the script does not break on a slower network — which is the
single most common way recorded automation dies.

## ADR-004 — Inline selector, alternatives in a comment

**Context.** Two goals collide. Generated code must be maintainable by hand, which
argues for one clean inline selector. Selectors break when pages change, which argues
for emitting the whole fallback cascade.

**Alternatives.** (a) Inline best selector only, drop the rest. (b) Emit a
`_locate(page, candidates)` helper with the full ranked list. (c) Inline the best one,
and add a comment with the alternatives only when the best one is already weak.

**Choice.** (c). The threshold is `score < 80`, i.e. anything below a `role` selector.

**Trade-off accepted.** Automatic fallback at runtime is given up for now: if the
selector breaks, a human fixes it, with the alternatives right there. (b) stays
available later behind a `--resilient` flag, generated from the same IR — the candidates
are all still in the recording either way.

## ADR-005 — Only the initial navigation is recorded

**Context.** Clicking a link fires a navigation event. Recording it produces a
`page.goto(...)` right after the click that caused it — code that re-navigates and
undoes its own step.

**Alternatives.** (a) Record every navigation. (b) Try to tell user-initiated
navigations from consequences. (c) Record only the initial URL.

**Choice.** (c).

**Trade-off accepted.** Typing a second URL into the address bar mid-recording is lost
and has to be added by hand. Distinguishing intent from consequence needs signals the
DOM does not reliably provide, and guessing wrong generates broken code — worse than
generating incomplete code.

## ADR-006 — CI, tests and strict typing are in scope, unlike a course project

**Context.** For a 45-minute-per-session learning project, skipping CI, strict typing
and a test suite is the correct call — they cost more than they return at that scale.

**Alternatives.** (a) Keep that calibration. (b) Treat tests, CI, strict `mypy`, semver
and packaging as part of the product.

**Choice.** (b), explicitly reversing the earlier posture.

**Trade-off accepted.** Slower feature delivery. Justified by what this project is:
code that runs on strangers' machines, captures their keystrokes, and is published
under the author's name. A bug here writes someone's password into a file on their
disk. Deliberately still out of scope: a GUI, macOS and Linux before v1.0, a plugin
system, cloud execution.

## ADR-007 — The working repository lives outside Google Drive

**Context.** The author's other projects live on a Google Drive-synced folder, without
a `.git` directory, because Drive corrupts repositories by syncing git internals
mid-operation.

**Alternatives.** (a) Keep it on Drive without git. (b) Keep it on Drive with git and
accept the risk. (c) Keep the working repository on local disk.

**Choice.** (c).

**Trade-off accepted.** No automatic Drive backup. Irrelevant here: for an open-source
project, the remote git host *is* the backup, and this project needs real history, tags
and branches, which (a) cannot provide.

## ADR-008 — English throughout, including code comments

**Context.** The author writes Portuguese. The first draft had Portuguese docstrings,
comments, CLI strings and generated-code variable names.

**Alternatives.** (a) Portuguese everywhere, translate later. (b) English-facing
documentation over a Portuguese codebase. (c) English everywhere.

**Choice.** (c), decided before publication rather than after.

**Trade-off accepted.** The author writes in a second language, and a Portuguese README
would have been better prose. But the stated goal is a tool anyone can use, (b) reads
as inconsistent to any contributor, and translating a codebase after it has forks and
issues is far more expensive than translating it now.

## ADR-009 — Named stepdub, after `encore` turned out to be taken

**Context.** The project was built under the name `encore`, chosen for the theatre
metaphor: an encore is a performance repeated on request.

**Alternatives.** (a) Keep `encore` as the project name and publish on PyPI as
`encore-recorder`, which was free. (b) Keep the name and rename only the CLI command.
(c) Pick a different name entirely.

**Choice.** (c) — `stepdub`. `step` is the unit of this domain (an `Event` is one
step) and `dub` is to re-record.

**Trade-off accepted.** The theatre metaphor is weaker, and a made-up word has no
meaning to lean on the first time someone reads it. In exchange, two blocking problems
go away. `encore` is already the CLI command of [encore.dev](https://encore.dev), a
prominent open-source backend framework: two binaries called `encore` on one PATH is a
hard conflict, not a branding preference, and "encore python" would never have found
this tool. The PyPI name `encore` is also taken (Enthought, last released 2022) and
would have stayed taken forever.

Verified free before choosing: PyPI, npm and GitHub. The only hits for "stepdub" are
music tracks, which do not compete for a developer's search. Two other candidates were
rejected on the same check: `remimic` belongs to an active deepfake product — a
terrible neighbour for a tool that has to argue it is not spyware — and `maczo` is
taken by a musician and an Apple reseller, and its "mac" prefix suggests macOS, the one
platform this project does not support.

**Timing was the point.** The rename touched the package directory, `pyproject.toml`,
the `STEPDUB_` environment variable prefix, `~/.stepdub`, the injected JavaScript's
globals and every document, in one commit. Once users have recordings on disk and
generated scripts reading `ENCORE_PASSWORD`, the same change becomes a migration.

## ADR-010 — Releases are built and published by CI, never from a laptop

**Context.** The first source distribution built on the author's machine contained a
private local notes file. It was ignored through `.git/info/exclude`, which git honours
and the build backend does not read, so it never appeared in `git status` and still
went into the archive. A PyPI upload cannot be taken back: a version can be yanked, but
the file is mirrored within minutes and its name can never be reused.

**Alternatives.** (a) Build locally, upload with an API token, and inspect every sdist
by hand. (b) Add an explicit sdist allowlist and keep uploading locally. (c) The
allowlist, plus building and publishing from GitHub Actions through PyPI Trusted
Publishing.

**Choice.** (c). The allowlist fixes this file; building in CI fixes the whole class,
because a file that was never committed does not exist on the runner. Trusted Publishing
means there is no long-lived API token anywhere to leak: PyPI trusts one workflow in one
repository. The release workflow runs the full CI on the tagged commit first, and
refuses to publish if the tag and the package version disagree.

**Trade-off accepted.** A one-time setup on PyPI, and no way to push out a hotfix from a
laptop: every release is a tag and a wait for CI. For a tool that asks strangers to
trust it with their keyboard, a release process that cannot leak the author's files is
worth the wait.
